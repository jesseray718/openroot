# OpenRoot Superloop Governance

## Purpose

The OpenRoot superloop is a local-first engineering support loop:

```text
observe → redact → retain evidence → classify → route → test
→ propose → human review → commit → CI → release decision
```

It improves recall, repeatability, and error recovery. It does not replace human responsibility for structural, electrical, thermal, water, food, safety, security, licensing, publishing, or deployment decisions.

## Canonical State

- Git repository: versioned source, documentation, schemas, workflow definitions, and reviewed defaults
- Local SQLite: operational job trail, local context metadata, routing outcomes, and non-public evidence
- JSON / JSONL: portable derived records and validated policy configuration
- GitHub Actions: deterministic remote verification and controlled release execution
- Public Gist: optional redacted status pulse only

## Automatic Actions

The loop may:

- Record sanitized command and task metadata
- Deduplicate evidence by cryptographic hash
- Classify a task into a documented routing bucket
- Suggest the least-cost capable local route
- Run allowlisted deterministic checks
- Generate a dashboard, report, patch proposal, test proposal, or issue draft
- Restart a non-privileged local daemon only through an explicit allowlist

## Human-Gated Actions

The loop must not autonomously:

- Commit, push, merge, tag, create a release, deploy, or alter repository settings
- Access, display, store, or publish tokens, private keys, recovery codes, credentials, raw secrets, or sensitive local records
- Run arbitrary shell text generated by a model
- Change model registry weights without evidence, review, and a reversible commit
- Publish a status pulse without redaction
- Treat model output as verified engineering, medical, legal, safety, or security guidance

## Evidence Standard

A pattern becomes a candidate rule only when it includes:

- Reproducible input or sanitized event identifier
- Observed result
- Proposed rule or routing adjustment
- Deterministic verification command
- Expected success and failure behavior
- Rollback path
- Human reviewer

## Permaculture Constraints

- Observe and interact: evidence before policy changes
- Catch and store energy: cache known-good routes and verified solutions
- Obtain a yield: each scheduled job must produce a useful measurable result
- Apply self-regulation: budgets, allowlists, rate limits, and review gates
- Produce no waste: deduplicate, expire, and compact derived operational data
- Use small and slow solutions: prefer local, reversible, low-resource actions
- Use edges: convert recurring exceptions into test cases
- Respond to change: treat drift as an experiment proposal, not automatic authority

## Data Hygiene

Never commit or publish:

- `.env`, credentials, tokens, keys, recovery codes, session cookies
- SQLite databases unless explicitly sanitized and intentionally versioned
- Raw command history or raw prompts
- Private hostnames, LAN addresses, user paths, or device identifiers
- Unreviewed telemetry, model transcripts, or error dumps
